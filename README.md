# workbench — heap_hunter vs Eclipse MAT benchmark

Benchmarks `hunt` (heap_hunter) against Eclipse MAT 1.17.0 on complicated HPROF
dumps generated by heap_forge `stress` profiles, under limited memory.

**Latest results:** [results/summary.md](results/summary.md)
(per-run data: [results/results.csv](results/results.csv) ·
[results/results.json](results/results.json) ·
correctness: [results/correctness-*.json](results/))

## Layout

- `dumps/`      generated HPROF dumps (`mixed-512m`, `mixed-2g`, `mixed-6g`)
- `runs/`       per-scenario work dirs (`hunt-<dump>-<cap>/`, `mat-<dump>-<cap>/`)
- `results/     results.csv, results.json, summary.md, correctness-<dump>.json
- `mat/`        unzipped Eclipse MAT 1.17.0 (see setup.sh)
- `mat-report/bench_extract.xml`  custom MAT report: histogram + dominator tree
  by class + overview, emitted as CSV under `dumps/<stem>_Bench/pages/`

## Usage

```sh
./setup.sh            # build hunt (ReleaseFast) + heapforge jar + install MAT (idempotent)
./gen-dumps.sh        # generate missing quick dumps (add --full for the 6g tier)
./bench.py --quick    # approved quick matrix
./bench.py --full     # full matrix incl. 6g tier
./bench.py --all-caps # run every cap (default stops at first successful index)
./bench.py --dump mixed-512m --hunt-budget 256 --mat-xmx 512m   # single scenario
```

Caps run from highest to lowest and the ladder stops at the first failed
index per tool; lower caps are skipped because they cannot rescue a failure
at a higher cap. `--all-caps` restores the exhaustive ladder.

## What is measured

Phases (timed separately, peak RSS recorded for every run):

| phase    | hunt                                             | MAT                                                          |
|----------|--------------------------------------------------|--------------------------------------------------------------|
| index    | `hunt index` + `hunt overview`                   | `ParseHeapDump.sh <dump>` (index build only)                  |
| histogram| `hunt histogram` (full CSV)                      | `bench_extract.xml` Histogram section (CSV)                   |
| dominator| `hunt dominator <id>` (retained size)            | `bench_extract.xml` dominator-tree-by-classloader section     |
| roots    | `hunt roots <id>`                                | (combined with MAT report run)                                |
| reports  | (combined with hunt queries)                     | suspects + top_components + bench_extract                     |

- Memory caps are **tool-level**: hunt `--sorting-budget-mb/--dominator-budget-mb`,
  MAT `-Xmx`. MAT index files are deleted between scenarios so each run re-parses.
- Peak RSS via `os.wait4` rusage (`ru_maxrss`), wall time monotonic.
- Child stdout/stderr go to temp files, not pipes: `hunt roots` on deep chains
  and MAT progress output exceed the 64 KB pipe buffer and would deadlock
  (nothing is read until the process exits).
- Status: `ok` / `fail` / `oom` (OutOfMemoryError detected) / `timeout` (killed).
  Under-budget hunt indexes fail cleanly with an actionable error
  (e.g. `dominator computation needs X MB ... raise it with --dominator-budget-mb`).
- Correctness cross-check: full hunt histogram CSV vs MAT `Histogram2.csv`
  (per-class instance counts, shallow bytes, totals; written to
  `results/correctness-<dump>.json` and `summary.md`). The MAT report emits
  the *unlimited* histogram (`<param key="limit" value="-1"/>`; the default
  caps report tables at 25 rows), and duplicate class rows in the MAT CSV
  are summed by the parser.

## Known correctness delta

Object counts agree within 0.3% at all tiers (chain-32 +0.26%, mixed-512m
-0.03%, mixed-2g -0.05%). Shallow byte totals differ ~6-10% because hunt and
MAT use different size models: hunt is smaller on instances and primitive
arrays (header/padding) and larger on reference arrays (8-byte elements vs
MAT's 4-byte compressed oops); the effects partially cancel. See the
per-class `top_diffs` in `results/correctness-<dump>.json`.

## Memory-cap strategy note

The original plan included hard cgroup caps (`systemd-run --user --scope
-p MemoryMax=...`). This was investigated and **does not work** in this WSL2
hybrid-cgroup environment: the unified (v2) hierarchy has no controllers
delegated to user slices (`cgroup.controllers` is empty), the v1 memory
hierarchy is root-owned, and `sudo` requires a password. Fallback (per plan):
tool-level caps only — both tools enforce their own limits (MAT via JVM heap
size, hunt via its external-sort budgets) and real peak RSS is measured for
every run, so over-budget behavior is still visible.
